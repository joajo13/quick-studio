# Epic 5 Context: AI Chat with Executable-JS Sandbox

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Fold a multi-provider AI assistant into the workspace: a developer configures their own API keys, asks a database question in natural language, receives a query bound to the active connection's schema, runs it from the chat, watches the model's reasoning and answer stream in, and sees rich MDX Blocks (Markdown + charts + executable JS) render safely. This epic owns the single highest-risk capability in v1 — the cross-origin, pure-render sandbox that quarantines LLM-generated JavaScript. It matters because the full AI chat (not a smaller query-helper) is a deliberate, marquee part of the product, and the sandbox it builds here is the hard prerequisite that also unblocks Epic 6's report exports. Stories are ordered so value arrives incrementally and the sandbox is de-risked early: provider config → chat/boundary → NL→query → streaming → sandbox → MDX. Provider config, chat, NL→query, and streaming all ship without the sandbox; only rich MDX rendering waits on it.

## Stories

- Story 5.1: Configure AI Providers with user-supplied API keys
- Story 5.2: Chat Q&A with the Core as sole Provider caller, schema-only by default
- Story 5.3: Natural-language to query + execution from chat
- Story 5.4: Streaming responses with visible reasoning
- Story 5.5: Cross-origin executable-JS sandbox with adversarial containment
- Story 5.6: Rich MDX rendering (Markdown + executable JS + charts)

## Requirements & Constraints

- Support Anthropic, OpenAI, and Google (Gemini) providers, each with the user's own API key; a configured provider is selectable per chat. There is no backend and no hosted cost — everything runs on the user's own account.
- Provider keys are protected exactly like database credentials: encrypted at rest in Persistent mode, session-only in memory and never written to disk in Ephemeral mode.
- A chat is bound to exactly one explicitly selected connection; generated queries target that connection's schema. Running a generated query must produce the same result as running it in a query tab.
- Destructive/DDL statements (DELETE/DROP/TRUNCATE/UPDATE/ALTER) generated by the AI are never auto-executed — they always require explicit confirmation, enforced by the same guarded executor built in Epic 3.
- Outbound provider payloads default to schema-only (table/column names, types, foreign keys). Row data leaves only via an explicit, per-query, visibly-indicated opt-in. No query results, schema, or report data go to any third party except the user-configured provider carrying only what was intentionally included.
- Responses stream token-by-token; the model's reasoning is shown as a channel visually distinct from the final answer. Streaming and MDX rendering must never jank the UI thread.
- Success is measured by conversational work reliably yielding the right query/info, and by rich in-chat charts/MDX Blocks actually getting used in real sessions — the usage that justifies the sandbox's cost.

## Technical Decisions

- **Three-ring trust model governs everything.** Ring 1 Core (Bun backend) holds all secrets, executes all SQL, and makes every outbound provider call. Ring 2 UI (React/shadcn) issues typed requests. Ring 3 is the untrusted sandbox. Data flows outward only; capability never flows inward.
- **Core is the sole provider caller.** Provider keys live only in the Core. The Core assembles one typed, inspectable payload with schema metadata and any opt-in row sample as **distinct fields**. Providers are never called from Ring 2/3.
- **Unified AI layer.** All providers are reached through the Vercel AI SDK (`ai` 7.0.15 + `@ai-sdk/anthropic`/`openai`/`google` 4.0.8) — never called directly. Streaming is delivered Core→UI over SSE on the localhost HTTP channel; reasoning travels as a channel distinct from the answer.
- **Cross-origin sandbox (the hard gate for MDX).** LLM-generated JS runs in an iframe served from a **separate origin**, with `sandbox="allow-scripts"` and **without** `allow-same-origin`, under CSP `default-src 'none'` and `connect-src 'none'`. In-process isolation (SES/QuickJS/ShadowRealm) is explicitly NOT the boundary. `postMessage` is one-way for data: Ring 2 pushes already-frozen data in; the sandbox emits out only render-lifecycle/interaction signals (ready, height, datum-clicked) and can never request data or trigger a query.
- **The sandbox ships with an adversarial containment test battery** proving cross-origin escape attempts, `connect-src` egress attempts, and inward data/query-request attempts all fail. The ring is not the boundary until someone has tried to cross it and failed.
- **Guarded executor reuse.** Queries run from chat pass through Epic 3's single Core executor as raw SQL (path b): default-deny on mutating/DDL statements, always parameterized. The confirmation dialog is UX only; the executor is the real gate.
- **Frozen-data contract.** Data pushed to the sandbox uses the single canonical, versioned frozen-data shape from `src/shared/` (defined in Epic 1) — ISO-8601 UTC dates, typed values. This is the same shape Epic 6 snapshots embed.
- **Charts split by ring.** Sandbox (Ring 3) charts use Observable Plot — Ring 3 has no React host. (In-app Ring 2 charts use Recharts, but those belong to Epic 6.)
- Source topology: chat/provider/streaming logic in `src/core/`, chat UI in `src/ui/`, sandbox host/guest in `src/sandbox/`, contracts in `src/shared/`.

## UX & Interaction Patterns

- AI Chat is one of the launcher-rail surfaces, opened as a tab like any other work unit. Provider configuration lives in the pinned Settings surface alongside connections.
- The reasoning channel must be rendered visually distinct from the final answer. Note: the workspace prototype does not include a visual treatment for the reasoning channel — Epic 5 owns it and it is flagged for a dedicated UX pass.
- Microcopy is mono, technical, lowercase, terse — reads like a status line, not marketing. DB identifiers are rendered verbatim from the live database, never re-cased.
- Motion serves feedback only (streaming, state changes); honor `prefers-reduced-motion`. Streaming must stay smooth and never jank the UI thread.
- Destructive/DDL statements run from chat surface a clear confirmation dialog before execution, shared with the query tab.

## Cross-Story Dependencies

- **Within the epic:** Story 5.6 (MDX rendering) is hard-gated by Story 5.5 (the sandbox). Stories 5.1–5.4 do not depend on the sandbox and can ship without it. The intended internal order is 5.1 → 5.2 → 5.3 → 5.4 → 5.5 → 5.6.
- **On other epics:** Depends on Epic 1 (Core↔UI channel, session token, frozen-data contract in `src/shared/`) and Epic 3 (the guarded Core executor that 5.3 reuses). Persistent provider keys depend on Epic 2's encrypted store; without it, keys are Ephemeral session-only.
- **Downstream:** The Story 5.5 sandbox and its charting are the prerequisite reused by Epic 6 (Local Report Generation) for MDX rendering and snapshot/live-report exports.
