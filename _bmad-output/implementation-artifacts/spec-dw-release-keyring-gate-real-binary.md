## Intent

**Problem:** DW-89. The release keyring gate (`.github/workflows/release.yml`, `build` job) compiles and runs a *second, different* artifact — `bun build --compile scripts/keyring-native-check.ts` — and never executes `quick-studio-<os>-<arch>`. It therefore proves the leg's **toolchain** can embed `@napi-rs/keyring`, not that the **published binary** can load it. The two are equivalent only by accident of a currently-static import chain (`bin/quick-studio.ts → first-run-setup.ts → … → keychain.ts`); the first lazy import of `keychain.ts` — a plausible startup-latency optimization — leaves the gate green while every shipped binary silently degrades all users to the passphrase fallback, the exact failure Story 11.2 exists to prevent.

**Approach:** Give the product a hidden, env-gated diagnostic entry — `QS_SELFCHECK=keychain` — that runs the same keychain round-trip and exits without booting the Core, and point the release gate at `./quick-studio-<os>-<arch>` with that variable set instead of at a stand-in artifact. The round-trip itself moves into one shared module that both the new branch and `scripts/keyring-native-check.ts` consume, so the spike path and the release path can never drift into "equivalent by accident" again.

## Boundaries & Constraints

**Always:**
- The release gate must execute **the artifact that is published** (`${{ matrix.asset }}`), not a separately compiled stand-in.
- The self-check branch resolves **before** `parseCliArgs`, `resolvePort`, `runFirstRunSetup`, and `startCore`, so no argv shape can mask it and it can never bind a port, create the app-data directory, write a lock file, or prompt for a passphrase.
- With `QS_SELFCHECK` unset or empty, behavior is **byte-identical** to today on every path (help, version, update, run, both modes).
- Pass/fail semantics stay exactly those of `scripts/keyring-native-check.ts`: addon loaded but no backend (`unavailable`) is a **pass**; a failure to load the addon at all is a **fail**; `KEYRING_REQUIRE_ROUNDTRIP=1` additionally demands a real round-trip and the structural `not-found` probe (DW-10).
- The round-trip is self-cleaning, never writes a real credential, and never logs a secret value.
- `scripts/keyring-native-check.ts` keeps its exact stdout/stderr line format, its exit codes, and its env contract — `.github/workflows/keyring-spike.yml` must remain untouched and keep working.
- The keychain module must stay reachable from `bin/quick-studio.ts`'s module graph by construction, so `bun build --compile bin/quick-studio.ts` always embeds the native binding.

**Block If:**
- If `bun bin/quick-studio.ts` cannot be spawned from `bun test` on this host (so the new branch has no automated proof at all), HALT rather than shipping an untested entry-point branch.

**Never:**
- Never expose `QS_SELFCHECK` in `HELP_TEXT` or the README environment table — it is a release-gate probe that mutates the OS keychain, not a user knob. `QS_NO_UPDATE_CHECK` is the in-repo precedent for a real-but-help-hidden variable; document this one in `docs/keyring-spike-decision.md` instead.
- Never add a fifth `CliArgs.action` variant or a field to `CliArgsEnv` — `action` is documented as deliberately flat and field-complete; the branch reads `process.env` directly, as `update-check.ts` does.
- Never delete `scripts/keyring-native-check.ts` or change what `keyring-spike.yml` runs.
- Never change `src/core/keychain.ts`, the Core's security surface, or any run-mode behavior.
- Never set `KEYRING_REQUIRE_ROUNDTRIP` on a release leg — the release gate proves addon-load; round-trip attestation stays with the spike workflow (Story 11.2 Design Notes).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Not requested | `QS_SELFCHECK` unset or `""` | No branch taken; CLI parses and boots exactly as today | none |
| Gate, backend present | `QS_SELFCHECK=keychain` on a host with a keychain | `stored` → `found (matches=true)` → `deleted`, `selfcheck: OK …` on stdout, exit 0, Core never boots | none |
| Gate, headless runner | `QS_SELFCHECK=keychain`, no Secret Service | every call returns typed `unavailable`, `selfcheck: OK …`, exit 0 | `unavailable` is a pass, never a failure |
| Gate, addon absent | `QS_SELFCHECK=keychain` on a binary that did not embed the binding | exit non-zero; if the throw reaches the branch, `selfcheck: FAILED — native module did not load: <msg>` on stderr | Loud, non-zero, no Core boot |
| Round-trip demanded | `QS_SELFCHECK=keychain` + `KEYRING_REQUIRE_ROUNDTRIP=1`, backend missing | `selfcheck: FAILED — KEYRING_REQUIRE_ROUNDTRIP=1 but no real round-trip …`, exit 1 | Hard failure by design |
| not-found contract | `KEYRING_REQUIRE_ROUNDTRIP=1`, never-stored account returns anything but `not-found` | `selfcheck: FAILED — a never-stored account returned "<outcome>" …`, exit 1 | DW-10 structural contract |
| Typo in CI | `QS_SELFCHECK=kaychain` | stderr `quick-studio: unknown QS_SELFCHECK 'kaychain' (want: keychain)`, exit 1 | Fails fast — must never fall through and boot the Core, which would hang the leg to its timeout |
| Argv ignored | `QS_SELFCHECK=keychain ./binary --persistent foo bar` | Self-check runs and exits; argv is never parsed | A usage error in argv cannot mask the self-check |
| Spike path unchanged | `bun build --compile scripts/keyring-native-check.ts && ./keyring-native-check` | identical `native-check: …` lines and exit codes as before this change | unchanged |

## Design Notes

**Why two new modules instead of one.** The branch must decide *whether* to self-check before it imports anything that touches `@napi-rs/keyring`. If `bin/` statically imported the round-trip module, an addon-load failure would throw during module evaluation — outside the branch's `try` — and the clean `selfcheck: FAILED — native module did not load` message would be dead code. `self-check.ts` is therefore dependency-free and statically imported; `keychain-self-check.ts` is dynamically imported inside the `try`. This is the same split `scripts/keyring-native-check.ts:34-39` already relies on, and `bun build --compile` still statically bundles a dynamic import with a literal specifier, so the addon is embedded either way.

**Honest scope of the load-failure message today.** Because `bin/quick-studio.ts → first-run-setup.ts → … → keychain.ts` is *currently* static, a binary with a missing binding already dies during module evaluation, before the branch executes — a loud, non-zero, but ugly failure. The branch's `catch` becomes the reporting site only once that chain goes lazy, which is precisely the future DW-89 is about. The gate is correct in both worlds; only the error message's tidiness differs.

**Why the unknown value fails instead of being ignored.** A gate that sets `QS_SELFCHECK=kaychain` and gets a silent fall-through would boot the Core on a CI runner and sit there until `timeout-minutes: 30` expires, reporting a hang instead of a typo. Exit 1 with the expected value named turns that into a five-second diagnosis.

**Keychain writes and the Ephemeral no-disk-write invariant.** The self-check stores and deletes one probe entry under the dedicated `quick-studio-native-check` service. It is not a run: it exits before mode resolution, before `runFirstRunSetup`, and before `startCore`, so it never reaches anything the Epic 2 invariant governs, and it touches no file on disk. It is the same footprint `scripts/keyring-native-check.ts` has always had, moved behind an env gate in the product binary.

**Contract letter vs. delivered implementation** (added by the 2026-07-28 follow-up review; the `<intent-contract>` block is frozen, so the reconciliation is recorded here rather than by rewriting it). Two clauses in the contract read, literally, as forbidding something the shipped change does. Both readings resolve the same way — the implementation serves the clause's stated purpose — and neither is an unresolved intent question:

- *"`.github/workflows/keyring-spike.yml` must remain untouched and keep working"* (Boundaries → Always). The change adds one `on.push.paths` entry to that file. The two halves of the clause are in tension precisely because this change moved the round-trip body out of `scripts/keyring-native-check.ts`: leaving the trigger list untouched would have orphaned the repo's only per-platform AR-20 attestation from the code it attests, making "keep working" false. The operative prohibition — the `Never` at *"change what `keyring-spike.yml` runs"* — is satisfied exactly: no job, step, leg, or `env` was touched.
- *"Never set `KEYRING_REQUIRE_ROUNDTRIP` on a release leg"* (Boundaries → Never). The gate step sets it to `""`. The clause's own rationale names what it protects — round-trip attestation stays with the spike workflow — and an empty value is non-strict, so the protection holds. Pinning it empty makes that structural instead of dependent on nobody defining the variable at workflow or job level, which is strictly stronger than leaving it absent.

**Shape of the branch** (goes above `parseCliArgs`):
```ts
const selfCheck = resolveSelfCheckMode(process.env);
if (selfCheck.kind === "unknown") { /* stderr + exit(1) */ }
if (selfCheck.kind === "keychain") {
  try {
    const { runKeychainSelfCheck } = await import("../src/core/keychain-self-check.ts");
    process.exit(runKeychainSelfCheck(process.env));
  } catch (err) { /* selfcheck: FAILED — native module did not load; exit(1) */ }
}
```
