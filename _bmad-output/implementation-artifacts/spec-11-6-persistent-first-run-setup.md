## Intent

**Problem:** On a host with no reachable OS keychain, Persistent mode can only be unlocked with a passphrase, and the **only** ways to supply one are the `QS_PASSPHRASE` environment variable and the `QS_PASSPHRASE_FD` file descriptor (`src/core/passphrase-provider.ts:144-160`). There is no interactive path. A user who runs `quick-studio --persistent` on such a machine — a headless Linux box, a container, a WSL session with no D-Bus — gets a store that reports `passphrase-declined` and a workspace that cannot save anything, with the only remedy buried in a README section about file descriptors. The seam for fixing this was designed in from the start and then never filled: the module header states plainly that "Story 2.4 injects an interactive prompt later through this same seam" (`passphrase-provider.ts:5-8`), and Story 2.4 shipped without it. This is the "setup" half of the epic's flow #3 — `--persistent` on a first run should *set the thing up*, not boot a store it cannot open.

**Approach:** Prompt **before** the Core boots, and inject the answer through the existing seam.
- The `PassphraseProvider` contract is **synchronous** (`(ctx) => PassphraseResponse`, `passphrase-provider.ts:45`), and an interactive terminal prompt is not. Rather than make the seam async — which would ripple through `openCredentialStore`'s total-boundary contract, `openPersistent`, and both store call sites — `bin/` performs a **pre-flight**: classify what the store will need, prompt asynchronously if it needs a passphrase, and hand `startCore` a pre-resolved provider closure that simply returns the captured value. The crypto layer is untouched.
- The pre-flight classification must **mirror** `openPersistent`'s existing branch logic (`credential-store.ts:527-611`): descriptor present → passphrase mode, prompt to unlock; descriptor absent but `.enc` present → keychain mode, no prompt; neither (true first run) → probe the keychain, and prompt only if it is unavailable.
- `startCore` gains an optional `passphraseProvider` in `StartCoreOptions`, defaulting to today's `resolvePassphraseProvider(process.env)` (`server.ts:269`) so nothing changes when no prompt happened.

## Boundaries & Constraints

**Always:**
- Echo is **disabled** while a passphrase is typed, and the terminal's original echo state is restored on every exit path — success, wrong passphrase, `Ctrl-C`, `Ctrl-D`, or an unexpected throw. Leaving a user's terminal with echo off is a serious, visible defect.
- The passphrase is **confirmed** (typed twice, compared) when creating a **new** store, and prompted once with a bounded retry budget when **unlocking an existing** one. `PassphraseContext.isFirstRun` (`passphrase-provider.ts:32`) already exists to carry exactly this distinction — the pre-flight computes it from the descriptor's presence.
- **One** provider instance is shared by both persistent stores, preserving the invariant documented at `credential-store.ts:518-522` and implemented at `server.ts:263-269`: the credential store and the provider-key store must never each consume a single-read source. A pre-resolved closure satisfies this naturally.
- The env and fd transports keep **absolute precedence**: if `QS_PASSPHRASE` or a valid `QS_PASSPHRASE_FD` is set, no prompt appears and behavior is byte-for-byte what it is today. The prompt is strictly a fallback for when neither is present.
- A **non-interactive** stdin never prompts. The process must not hang waiting for input that can never arrive; it falls through to today's typed `declined` outcome plus a pointer to `QS_PASSPHRASE_FD`.
- The keychain probe uses the existing wrapper (`src/core/keychain.ts`), which is already total and returns typed `not-found` / `unavailable` — never a throw and never a plaintext fallback.

**Block If:**
- If the pre-flight classification cannot be kept in lockstep with `openPersistent`'s branch logic, HALT and restructure instead: the two must not be independent re-implementations that can drift, because a drift means prompting when the store will not ask (a pointless prompt) or not prompting when it will (the bug we are fixing). Prefer extracting the classification into one shared, pure function consumed by both.
- If disabling terminal echo cannot be done reliably on **Windows** consoles under Bun with `node:readline`/raw-mode, flag it before implementing — a prompt that echoes a passphrase to the screen is worse than no prompt at all, and the correct fallback is to skip prompting on that platform and keep today's env/fd behavior.

**Never:**
- Never echo, log, or write the passphrase anywhere. Never place it into `process.env` — the whole point of the fd transport (`passphrase-provider.ts:52-59`) is that the environment is a known leak surface, and a prompt that then exports the secret would defeat it.
- Never prompt in **Ephemeral** mode (no store is ever opened) and never prompt when the keychain is available.
- Never prompt on a non-TTY stdin, and never block boot waiting for input.
- Never weaken, bypass, or reorder any existing store-open path: the descriptor is still authoritative, a declined passphrase still writes nothing (no descriptor, no ciphertext, no plaintext), and the advisory writer lock (`store-lock.ts`) is unaffected.
- Never retry unlocking without a bound.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Keychain available, first run | Persistent, no descriptor, no `.enc`, keychain reachable | No prompt; keychain path exactly as today | none |
| Keychain unavailable, first run, TTY | Persistent, no descriptor, no `.enc`, keychain `unavailable`, interactive stdin | Explain why, prompt with echo off, **require confirmation**, then boot with the store created in passphrase mode | Mismatch → re-prompt within the retry budget |
| Keychain unavailable, existing store, TTY | descriptor present, interactive stdin | Single prompt (no confirmation), bounded retries on a wrong passphrase | Exhausted retries → today's typed failure, nothing written |
| Env transport set | `QS_PASSPHRASE` non-empty | **No prompt**; unchanged behavior | none |
| Fd transport set | `QS_PASSPHRASE_FD=3` valid | **No prompt**; unchanged behavior, single-read semantics preserved | none |
| Fd transport malformed | `QS_PASSPHRASE_FD=abc` | **No prompt** — the operator explicitly opted out of the env transport (`passphrase-provider.ts:157-159`), and prompting would be a third silent fallback they did not ask for | Declines exactly as today |
| Non-TTY stdin | piped/CI/service manager, no env, no fd | No prompt, no hang; typed `passphrase-declined` + a stderr pointer to `QS_PASSPHRASE_FD` | Fail fast |
| Ctrl-C during the prompt | user aborts | Terminal echo restored, clean exit, nothing written to disk | Must not leave echo off |
| Ephemeral mode | `quick-studio postgres://x` | No prompt, no store, no disk — unchanged | Hard invariant |
| Both stores | credential store + provider-key store in one boot | Exactly **one** prompt; both stores unlock from the same captured value | Never two prompts |
| Descriptor absent, `.enc` present | Story 2.2 back-compat layout | Keychain mode; **no** prompt, mirroring `credential-store.ts:571-576` | Classification must match |

## Code Map

- `src/core/passphrase-provider.ts` — add two pure exports, no change to existing behavior: `hasPassphraseTransport(env)` (true when `QS_PASSPHRASE_FD` is present-and-non-blank **or** `QS_PASSPHRASE` is non-blank — the "an operator already chose a transport" predicate, mirroring the precedence at `:144-160`), and `staticPassphraseProvider(passphrase)` → a `PassphraseProvider` closure that ignores `ctx` and always returns `{outcome:"provided", passphrase}`. The sync `PassphraseProvider` seam (`:45`) is **not** made async.
- `src/core/store-presence.ts` (new, shared with Story 11.7) — pure, injectable-`fs` presence probe over the app-data directory. `classifyStorePresence(dir, deps)` → `{ credential, providerKeys }`, each `"passphrase-mode" | "keychain-mode" | "first-run"` from `existsSync` on the four constants re-exported from their owners (`STORE_META_FILE_NAME`/`STORE_FILE_NAME` in `credential-store.ts:79,92`; `PROVIDER_STORE_META_FILE_NAME`/`PROVIDER_STORE_FILE_NAME` in `provider-key-store.ts:56,62`). **No decryption, no key load, no lock, no `ensureAppDir`.** Plus `anyDescriptorPresent(presence)` — the create-vs-unlock discriminator. This file is what Story 11.7 will reuse; keep it free of any prompt/boot concern.
- `src/core/passphrase-prompt.ts` (new) — the interactive prompt. `isInteractive(deps)`; `promptPassphrase(label, deps)` (single read); `promptNewPassphrase(deps)` (read + confirm, bounded mismatch budget). Async, fully dependency-injected (`input`, `output`, `createInterface`) so it is tested with fake streams, never a real terminal. Returns `{outcome:"provided", passphrase} | {outcome:"declined", reason}` with `reason ∈ "non-tty" | "aborted" | "empty" | "mismatch" | "unsupported"`.
- `src/core/first-run-setup.ts` (new) — the orchestration, in `src/core` (not `bin/`) so it is unit-testable; `bin/` stays a thin caller. `runFirstRunSetup(mode, env, deps) → Promise<FirstRunSetupResult>` where `FirstRunSetupResult = {outcome:"provider", provider} | {outcome:"skip"} | {outcome:"aborted"}`. `skip` means "change nothing, `startCore` resolves its own provider exactly as today"; `aborted` means the user pressed `Ctrl-C` and only `bin/` may act on it (this module never calls `process.exit`). Deps bag: `{ dir?, openCredential, openProviderKeys, presence, prompt, promptNew, isInteractive, stderr }`, defaults wired to the real modules. `dir` is a **test-only override**: in production it is omitted so each store resolves the app dir itself (`ensureAppDir()`), and `classifyStorePresence` uses the *pure, non-creating* `resolveAppDir(process.env, process.platform)` (`app-dir.ts:43`) — never `ensureAppDir`, so no code path can create a directory before the Persistent-mode guard has passed.
- `src/core/credential-store.ts` / `src/core/provider-key-store.ts` — **consumed unmodified** as the classifier of record. `openCredentialStore(deps)` (`:449`) and `openProviderKeyStore(deps)` (`:343`) both accept `{mode, dir, passphraseProvider}` and return the same `OpenResult` union (`credential-store.ts:149-162`). Their existing `openPersistent` branch logic (`:522-668`) is **not** re-implemented anywhere — see Design Notes for how this discharges Block-If #1.
- `src/core/server.ts` — add optional `passphraseProvider?: PassphraseProvider` to `StartCoreOptions` (`:335-373`); at `:528` default it: `options.passphraseProvider ?? resolvePassphraseProvider(process.env)`. The **one** resolved instance keeps flowing unchanged into both `createConnectionRegistry` (`:530-532`) and `createProviderRegistry` (`:544-546`) — the single-shared-provider invariant documented at `:522-528` is preserved by construction.
- `bin/quick-studio.ts` — one `await`ed call to `runFirstRunSetup(...)` inside the existing outer `try` (`:78-148`), immediately before the `startCore` call at `:88-95`, threading the result into the new option. Placement is after the `help`/`version`/`update` early exits (`:60-76`), so those paths never prompt.
- `src/core/keychain.ts`, `src/core/store-key.ts` — **not called directly** by this story. `loadOrCreateStoreKey()` (`store-key.ts:95`) can return `outcome:"created"`, i.e. probing through it *mints* a keychain entry; keychain availability is instead learned from the store-open probe (Design Notes).
- `README.md` — document the interactive first-run prompt: when it appears (Persistent + no `QS_PASSPHRASE`/`QS_PASSPHRASE_FD` + keychain unreachable + TTY), that it never appears in Ephemeral or on a non-TTY, and that `QS_PASSPHRASE_FD` remains the non-interactive path. Mirror the existing env-var section phrasing.
- Tests — `src/core/store-presence.test.ts`, `src/core/passphrase-prompt.test.ts`, `src/core/first-run-setup.test.ts`, co-located per repo convention, `bun:test`, table tests + a spy `deps` factory asserting exact call counts (the `update-check.test.ts:144-193` pattern).

**Acceptance Criteria:**
- Given a Persistent boot where a passphrase is required and stdin is a TTY, when the pre-flight runs, then the prompt completes **before** `startCore` is called and the Core boots with the captured passphrase already resolved.
- Given the pre-flight returns a provider, when both the connection registry and the provider-key registry later open their stores, then both receive the **same** provider instance and exactly one prompt was shown for the whole boot.
- Given `runFirstRunSetup` returns `skip` for any reason, when the Core boots, then behavior is byte-for-byte what it is today (`resolvePassphraseProvider(process.env)` resolved inside `startCore`), including the typed `passphrase-declined` outcome surfaced on first RPC.
- Given the user presses `Ctrl-C` at any prompt, when the pre-flight returns, then `bin/` exits 130 without booting the Core, no descriptor, ciphertext, or plaintext was written, and the terminal still echoes.
- Given any prompt path terminates — success, blank, mismatch, exhausted retries, SIGINT, or an unexpected throw — when the process continues or exits, then the readline interface was closed exactly once and no typed character was ever echoed.
- Given `quick-studio --help`, `--version`, or `update`, when it runs, then no probe, no `ensureAppDir`, and no prompt occur.

## Design Notes

**Block-If #1 (classification drift) — discharged, no HALT.** The draft proposed a `store-presence.ts` that re-derives `openPersistent`'s branch logic; investigation showed that logic is *not* cleanly extractable — the "true first run" arm (`credential-store.ts:603-666`) folds the decision together with its side effects (salt generation, descriptor write at `:642`, eager `.enc` write at `:654`, rollback at `:657-661`), and it runs while holding the DW-14 writer lock acquired at `:482`. So instead of re-implementing it, the pre-flight **asks the real function**: it calls `openCredentialStore` with a provider that always declines. `passphrase-declined` means "this store will ask for a passphrase"; `opened` means it will not; every other outcome means it has a different problem that a prompt cannot fix. There is exactly one implementation of the branch logic, so drift is structurally impossible. `store-presence.ts` survives only for the narrow create-vs-unlock question (descriptor presence — the `:551` vs `:617` split, which is a plain `existsSync` fact, not a branch re-implementation) and because Story 11.7 needs a presence-only probe anyway.

**Why not probe the keychain directly.** `loadOrCreateStoreKey()` (`store-key.ts:95`) is get-**or-create**: `outcome:"created"` means the probe just minted a durable keychain entry. `keychain.ts` offers no cheap reachability ping — only real `getSecret`/`setSecret` round-trips. The decline-probe answers the same question with zero extra native calls beyond the ones the store would make anyway.

**Two descriptors, one passphrase.** `provider-key-store.ts` keeps its own `provider-keys.meta.json`/`.enc` (`:56,62`) alongside the credential store's (`credential-store.ts:79,92`), and both are unlocked by the one shared provider. Create-vs-unlock therefore keys off **either** descriptor: prompting for a *new* passphrase while a provider-key descriptor already exists would mint a credential store the provider-key store cannot open. Verification targets whichever store actually holds a descriptor.

**Why the pre-flight opens and closes stores.** The registries are lazy — `startCore` never opens a store (`server.ts:519-521`), and open failures become typed `internal_error` RPC results, invisible to `bin/`. So the pre-flight is the only place a wrong passphrase can be detected in time to re-prompt. `close()` releases the writer lock via the latched release (`credential-store.ts:783-794`), so the later lazy open is unaffected; a concurrent instance holding the lock surfaces as `locked` → no prompt.

**Block-If #2 (Windows echo) — resolved by design, no HALT.** Muted `node:readline` is chosen over a hand-rolled raw-mode loop: the interface owns raw mode, line editing, EOF, and SIGINT delivery on all platforms, and suppressing echo is a `_writeToOutput` override — the standard Node password recipe, which is line-discipline-level and not Bun-internals-level. The residual risk is Windows-console parity under Bun and, separately, under `bun build --compile`; it is contained rather than blocked: `createInterface` throwing → `declined:"unsupported"` with the terminal never touched, which degrades to exactly today's env/fd behavior. Windows/compiled-binary confirmation is a manual check below, following the `keyring-spike.yml` precedent.

**Accepted limitation.** If the credential store opens via the keychain while the provider-key store is in passphrase mode (only reachable by hand-editing the app dir), no prompt appears and the provider-key store surfaces its typed failure as it does today.
